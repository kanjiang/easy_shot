# 拍照姿势助手 App 设计文档

- 状态: Draft (v3 — 单屏实时引导 + 同系统双机协同)
- 日期: 2026-04-28
- 适用平台: HarmonyOS NEXT (V1)、HarmonyOS 4.x 兼容 (V1.5 视情况)、Android (V2)
- 形态: 移动端 App（单屏手机优先，支持同系统双机协同）
- 当前版本目标: 端侧 + 云端混合 AI 的 MVP，V1 在 HarmonyOS NEXT 上落地单屏拍照助手，并扩展同系统双机导拍 Beta；Android 在 V2 由跨端共享层扩展

## 1. 产品定位

帮助不会摆姿势的人，在拍照时获得清晰、可执行的姿势、构图、光线、风格建议；在拍后获得改进复盘。MVP 阶段不追求覆盖所有摄影场景，而是把“给一句话能照做”的拍摄助手做扎实。

核心价值主张：

- **拍前**: 选风格 → 给到风格化的姿势模板和构图要点
- **拍中**: 单屏相机预览叠加 AI 虚拟模特示范、对齐框、一句实时纠正；双机模式下让辅助机同步看到导拍界面
- **拍后**: 给可执行的复拍建议，让用户慢慢学会怎么拍

产品体验可以参考双屏相机的“导演视角”思路，但本产品默认围绕单屏手机成立；即使用户只有一台手机，也能完整获得实时引导。

非目标（MVP 不做）：

- 不做社交社区/相册分享平台
- 不做美颜滤镜/重图像后期
- 不直接使用明星姓名、明星照片或刻意生成明星相似脸的 AI 内容
- 不做支付、订阅、企业版

## 2. 用户与场景

主要用户：18-35 岁、有拍照分享需求、但缺乏摆姿势/构图经验的普通用户。

核心拍摄场景（V1 全部覆盖，能力分层）：

1. **单人日常**: 街拍、咖啡店、公园、旅行打卡
2. **自拍/前置镜头**: 脸部角度、表情、手势、光线提醒
3. **朋友帮拍**: 同时给摄影者构图/机位建议，给被拍者动作建议
4. **双机协同导拍**: 一台主拍机负责取景和拍摄，另一台同系统手机显示导拍界面、实时提示，并可远程切模板与触发快门

## 3. 核心体验流程

### 3.1 主流程

```
启动应用
  ↓
首页：选择「风格 + 场景 + 拍摄模式」
  ↓
姿势模板列表（按风格、场景、镜头方向过滤）
  ↓
姿势详情页：AI 虚拟模特 + 局部手势/动作标注 + 动作口令
  ↓
进入相机 / 发起双机协同：实时姿势引导
  ↓
拍摄
  ↓
拍后复盘：照片预览 + 可执行复拍建议
  ↓
返回首页 / 再拍一张 / 换模板
```

首页新增模式切换：

- 单屏自拍
- 单屏朋友帮拍
- 双机导拍

### 3.2 拍中实时引导（单屏模式）

相机预览叠加 3 层信息：

1. **半透明姿势影子**: 用骨架（圆 + 线）画出目标姿势位置和比例，用户只需要把自己对齐
2. **局部对齐框**: 例如剪刀手目标位置画红色虚线圆，提醒手放到这里
3. **一句文字提示**: 始终只显示一句最关键的纠正，例如“右手剪刀手再靠近脸颊一点，手肘离身体远一点”

附带状态指示：

- 完成度百分比（基于关键点距离），例如 “完成度 68%”
- 重要部位红/黄/绿标记（高级模式开关，默认关闭，避免画面信息过多）
- 光线/构图实时建议（见 §5）

### 3.3 拍后复盘

拍完后给一张照片预览，加 1-3 条结构化建议，例如：

- 光线: 脸部略暗，建议下次向窗边移动一步
- 构图: 人物可放在画面右 1/3
- 姿势: 右手剪刀手贴脸颊会更甜美

每条建议附带 “按建议再拍一张” 按钮，引导回到相机界面，并把对应建议直接显示成实时提示。

### 3.4 双机协同导拍（伴侣屏）

灵感来自 Pura X Max 双屏取景，本产品用两台同 App 鸿蒙手机替代双屏，常见使用场景：

- **朋友帮拍**：摄影者持 A 机取景；被拍者持 B 机站到镜头里，B 机可看到自己被怎么拍、被怎么指导
- **一人自拍 (一人模式)**：自拍架/三脚架上放 A 机取景，被拍者拿 B 机当遥控屏 + 引导屏，B 机直接按下快门完成自拍

体验设计：

1. 角色：A = 主拍机 (Capturer)，B = 伴侣屏 (Companion)。两机都在“导拍模式”入口下选择角色
2. 配对：基于 HarmonyOS 分布式能力直接发现同账号或同 WLAN 设备 → 用户在 A 机上选 B 机后弹窗确认 → 双方信任建立后开始流转
3. 同步内容（默认）：
   - A 机相机预览镜像（按需降采样到 540p / 15-20 fps，节省带宽与电量）
   - 当前模板的姿势影子、局部对齐框、完成度
   - 一句实时纠正提示（A 与 B 完全一致）
4. B 机操作能力（明确为 V1 P0）：
   - **快门按钮**：辅助机底部固定一个明显的拍照按钮，按下即触发主拍机快门，支持 0/3/5/10s 倒计时；按下时辅助机给震动 + 主拍机提示音/闪屏，告诉用户即将拍摄
   - **取消快门**：倒计时未结束前可一键取消，主拍机随之取消
   - **切换姿势模板**：左右滑动或在面板里切换；切换后双端立即更新姿势影子
   - **暂停/恢复同步**：临时关掉预览镜像以省电，仅保留提示文本
   - **举手反馈“已就位”**：通知主拍机，可在主拍机界面浮一个轻提示（朋友帮拍时用）
5. 一人模式下 B 机为主操作界面，A 机自动进入“支架模式”：屏幕仅显示当前帧 + 完成度，避免误触
6. 终止：A 机或 B 机均可断开，断开后双方回到单屏模式且不丢失当前模板

可降级：

- 若网络抖动，自动从 “实时预览镜像” 降级为 “仅同步姿势卡 + 提示文字”，并提示用户带宽不足
- 若分布式能力不可用（例如非鸿蒙、跨账号、不同 WLAN），明确告知“当前环境暂不支持双机协同”

非目标（V1 不做）：

- 跨系统互联（鸿蒙 + 安卓）放到 Android V2 之后再评估
- 跨网络中转（云端 TURN）暂不做，避免成本和合规复杂度

## 4. 姿势模板系统

### 4.1 模板结构

每个姿势模板是一条结构化数据：

```jsonc
{
  "id": "pose_sweet_scissors_cheek_v1",
  "title": "剪刀手脸颊边",
  "style_tags": ["甜美日常", "校园感"],
  "scene_tags": ["室内", "街拍", "咖啡店"],
  "shot_type": "half_body",          // full_body / half_body / selfie
  "camera_facing": "front_or_rear",
  "difficulty": "easy",
  "description": "右手剪刀手放在右脸颊旁，手肘离身体远一点；下巴微收。",
  "verbal_steps": [
    "身体侧 15° 朝镜头",
    "右手比剪刀手贴近右脸颊",
    "手肘离身体远一点",
    "下巴微收，看镜头"
  ],
  "avatar_image": "assets/avatars/sweet/scissors_cheek_v1.png",
  "annotations": [
    { "label": "剪刀手贴脸颊", "anchor": { "x": 0.74, "y": 0.18 } },
    { "label": "下巴微收",   "anchor": { "x": 0.45, "y": 0.32 } }
  ],
  "skeleton": {
    "keypoints": [
      { "name": "nose",      "x": 0.50, "y": 0.20 },
      { "name": "right_wrist", "x": 0.70, "y": 0.22 },
      { "name": "right_elbow", "x": 0.78, "y": 0.34 }
      // ... 其他关键点
    ],
    "tolerance": 0.08
  }
}
```

字段约束：

- `avatar_image` 必须是项目自有授权或 AI 原创生成图，统一风格（清透甜美插画风），**不允许长得像任何明星**
- `skeleton.keypoints` 用归一化坐标 (0~1)，便于和实时 pose detection 输出对齐
- `verbal_steps` 不超过 4 条，每条不超过 18 个字
- `annotations` 用于姿势详情页和实时提示锚点

### 4.2 内容来源与版权

- AI 模特统一使用项目自建的**虚拟人设**（固定几套脸 + 服装组合），通过受控提示词生成，避免随机相似真人
- 姿势库由产品/摄影师整理，可参考公开摄影教程和通用风格语料；**不直接使用明星姓名或照片**
- 风格命名采用通用描述，例如：甜美日常、清冷街拍、元气校园、旅行氛围、复古胶片、清晨咖啡馆，**不使用明星名**

### 4.3 模板分类与检索

首页按 4 个维度筛选：

- 风格（必选 1 个）
- 场景（可多选）
- 镜头方向（自拍 / 朋友帮拍 / 全部）
- 难度（默认 easy）

后台保留扩展字段：人物数量、季节、主色调，方便后续扩展。

## 5. AI 能力设计

采用**端侧 + 云端混合**：

| 能力 | 端侧 | 云端 | 说明 |
|------|------|------|------|
| 人体关键点检测 | ✅ | - | MediaPipe Pose / 平台原生 ML 框架，30fps 级别 |
| 手部关键点检测 | ✅ | - | MediaPipe Hands |
| 姿势对齐计算 | ✅ | - | 关键点距离 + 角度对比模板 |
| 场景分类（室内/室外/天空占比） | ✅ | - | 端侧轻量分类模型，仅产出标签 |
| 光线/构图提示规则（含逆光） | ✅ | - | 简单规则引擎，使用相机亮度+场景标签综合判断（见 §5.2） |
| 风格化拍摄建议文案 | - | ✅ | 调用云端 LLM，生成具体到“调整角度/光线”的建议 |
| 拍后复盘建议 | 部分 | ✅ | 端侧出基础规则，云端做更自然语言化的总结 |
| 姿势模板检索/推荐 | - | ✅ | 后续做个性化排序 |

端侧首选理由：

- 实时引导必须低延迟（端侧推理 P95 < 80ms，详见 §11）
- 拍照场景属于隐私敏感，画面不应默认上传
- 离线也能基本可用

云端只用于：

- 拍摄前/后“一句具体建议”的生成
- 模板检索和后续推荐
- 不上传原始相机画面，仅传必要的统计/标签或用户主动选择上传的照片

### 5.1 姿势对齐算法（端侧）

输入: 模板 `keypoints`（归一化）和实时检测得到的人体关键点。

步骤:

1. 把实时关键点按用户人体框做归一化对齐（中心点对齐、按肩宽缩放）
2. 计算每对关键点的欧氏距离 `d_i`
3. 计算 `score = max(0, 1 - sum(d_i * w_i) / tolerance_total)`
4. 标记每个部位状态: `green: d_i < 0.5*tol`, `yellow: 0.5*tol <= d_i < tol`, `red: d_i >= tol`
5. 按部位优先级（脸 > 手 > 肩 > 腿）选出当前最该提的一条提示

部位权重和优先级写在配置里，便于后续按场景调整。

### 5.2 光线 / 构图规则引擎（端侧）

基于相机预览的轻量分析：

- 直方图判断曝光（脸部 ROI 平均亮度）
- 主体位置（人体框中心）相对画面 1/3 线的偏离
- 简单背景判断：天空占比、是否大面积同色（适合纯背景）
- 逆光检测：人脸 ROI 暗、背景亮 → 提示用户改变角度，例如“侧身让光线从左侧打来”

输出标准化事件：

```json
{ "type": "lighting", "level": "low", "advice": "脸部偏暗，建议向窗边走一步" }
{ "type": "composition", "advice": "人物可移到画面右 1/3" }
{ "type": "back_light", "advice": "正在逆光，转身让光从侧面打过来会更好看" }
```

实时提示模块按以下优先级显示：姿势 > 逆光 > 曝光 > 构图（每次只显示一条）。

### 3.4 双机协同导拍流程

双机模式中定义两个角色：

- **主拍机**: 打开相机、执行端侧 AI 检测、最终拍照与存储
- **辅助机**: 显示简化实时预览、当前姿势模板、关键纠正提示，并提供远程控制按钮

双机模式流程：

```
主拍机选择模板
  ↓
发起设备发现 / 配对
  ↓
辅助机加入会话
  ↓
主拍机本地完成姿态、光线、构图分析
  ↓
同步导拍状态到辅助机
  ↓
辅助机点击「拍摄 / 倒计时 / 下一模板」
  ↓
主拍机执行命令并完成拍照
  ↓
拍后复盘可回传到辅助机查看
```

辅助机界面坚持“导演视角”的信息极简原则，只显示：

- 当前实时预览或低帧率预览缩略流
- 1 条当前最重要提示
- 完成度与连接状态
- 远程控制按钮：拍摄、3 秒倒计时、上一模板、下一模板

### 5.3 风格化文案生成（云端）

输入: 当前模板 id、风格标签、场景标签、端侧识别到的事件（光线、构图）、用户输入的自由风格描述。

输出: 一段不超过 60 字的拍摄指南，使用 / 关注角度、光线、构图、人物动作四个维度中的相关项。

前端做兜底: 如果云端不可用，回退到本地静态文案库。

### 5.4 用户输入风格的处理

用户在搜索框输入“清冷感的街拍”“暖光下的旅行”等：

1. 端侧把输入做规范化（trim、长度限制）
2. 调用云端意图理解，匹配到内置风格标签集合（最多 3 个）
3. 用匹配标签筛选模板列表，并生成一段“风格说明”，例如：清冷街拍要点是冷色调、不直视镜头、留出空背景

## 7. 平台与技术架构

### 7.1 渐进式平台策略

- **Phase 1 / 原型 MVP (HarmonyOS NEXT)**: 先做 HarmonyOS NEXT，形成单屏闭环能力，并追加同系统双机导拍 Beta。技术栈使用 ArkTS + ArkUI（声明式 UI），相机使用 Camera Kit，端侧 AI 使用 HMS Core ML Kit / HiAI Foundation 中可用的姿态检测能力，并在设备互联层保留抽象接口。
  - 选 HarmonyOS NEXT 作为 V1 原因：用户优先级要求；同时 NEXT 不再兼容 APK，必须原生实现，迟早要做
  - 相机预览叠加层使用 ArkUI 的 `Stack`/`Canvas` 组件
  - 双机导拍优先使用 HarmonyOS 同系统设备发现与分布式连接能力，保证低门槛配对与控制链路
- **Phase 1.5 / HarmonyOS 4.x 兼容 (可选)**: 若需要在仍可装 APK 的 4.x 设备上覆盖更多用户：
  - UI 复用 ArkTS（4.x 同样支持），但要避免使用 NEXT 独有 API
  - 兼容性策略写在 “风险与开放问题” 中
- **Phase 2 / 扩展 Android**: HarmonyOS V1 体验稳定后再做 Android：
  - Android 用 Kotlin + Jetpack Compose + CameraX + MediaPipe Tasks
  - 共享层放在 `core/` 子工程：模板 JSON schema、姿势对齐算法、规则引擎接口、双机会话协议
  - 共享层尽量用纯算法 + 数据类，避免依赖任何平台特定 API；可用 C++ 实现 + 双端绑定（HarmonyOS Native API、Android JNI）

### 7.5 设备互联设计

V1 双机模式采用“主拍机计算、辅助机展示与控制”的非对称架构：

- 主拍机负责相机取流、端侧 AI、快门控制、照片存储、拍后复盘生成
- 辅助机不做重计算，只订阅主拍机同步的导拍状态，避免双端重复推理导致功耗翻倍
- 导拍状态包含：当前模板 id、模板标题、完成度、单条实时提示、主体框/推荐构图框、连接质量、倒计时状态

传输策略：

- 控制信令优先级最高：拍摄、倒计时、切模板、退出会话
- 预览同步采用降级设计：优先低延迟预览流；链路变差时退化为低帧率 JPEG 缩略图；再差则退化为仅状态文本和构图框
- 会话生命周期包括：发现、配对、授权、进入导拍、拍摄中、断连重连、结束会话

交互约束：

- 同一时刻只有一台主拍机，避免双端都持有相机资源
- 辅助机只能发高层命令，不能直接访问主拍机相册或原始图像文件
- 双机模式必须支持一键回退到单机模式，网络差时不影响主拍机本地拍照

## 8. 隐私与合规

- 默认所有姿态识别、画面分析在本地完成，**不上传相机画面**
- 云端建议只接收: 模板 id、风格/场景标签、端侧规则事件、用户输入的风格文本
- 拍后复盘如果用户主动“让 AI 看一下这张照片”，才上传照片，且明确文案告知
- 不收集明星照片，不在提示词中使用明星姓名
- 提供“纯本地模式”开关：完全不调云端，使用静态文案库
- 双机协同模式下，画面与导拍状态仅在已配对的两台设备间局域网直连传输，不经过云端中转；辅助机不能下载或保存主拍机的原始照片
- 双机协同的设备发现与配对必须用户在两端各自显式确认，并提供“一键解绑”入口
- 上线前完成 Android/HarmonyOS 各自的隐私权限说明、隐私政策页

## 10. V2 规划：拍照地图与打卡推荐

V2 增加“拍照地图”能力：

### 10.1 功能描述

- 用户在地图上输入或定位到某地点
- 应用查询周边可拍照打卡点（咖啡店、公园、地标、特色街区）并标注在地图上
- 每个打卡点附加：推荐风格、推荐时间段（光线）、推荐姿势模板、用户作品略缩图（如果未来开放分享）
- 进入打卡点详情，可一键“去拍”，跳转相机并预设对应风格和姿势模板

### 10.2 技术要点

- 地图: Android 选 高德/百度/Google Maps SDK 之一（按发布区域决定，不在本文档固化）；鸿蒙用 Petal Maps 或 HarmonyOS 地图能力
- POI 检索: 优先复用所选地图厂商的 POI/搜索 API，叠加自定义“拍照打卡”标签库
- 自有打卡点库: 初期由运营/众包整理，结构包含位置、风格标签、最佳时段、AI 生成示范图、推荐模板 id
- 个性化推荐: 基于用户风格偏好和位置，云端做排序，端侧仅展示
- 隐私: 位置使用需要明确授权；记录用户访问 POI 的行为时仅用本地匿名 ID

### 10.3 信息架构变化

新增 [拍照地图] 一级入口；[打卡点详情] 复用姿势详情卡片格式 + 地图位置块；相机入口在“去拍”时携带 POI id 用于复盘统计。

V2 仍然不做用户社交/分享，避免变成内容社区。

## 12. 风险与开放问题

- HarmonyOS NEXT 上的姿态/手势检测 API 可用性、SDK 接口和精度需要在 Phase 1 早期做 spike 验证；若 HiAI/CoreVisionKit 当前 API 能力不足，回退方案是用 MindSpore Lite 跑自训练或开源模型（如基于 BlazePose 的 ONNX）
- HarmonyOS 同系统设备发现、低延迟预览同步与后台保活能力需要早期做 spike；如果实时预览延迟过高，V1 Beta 需退化为“状态同步 + 远程拍照”模式
- HarmonyOS 4.x 兼容只在 V1.5 评估；NEXT 与 4.x 在 ArkUI 行为上有差异，需要专门 spike
- AI 虚拟模特素材的生产管线需要单独规划（提示词模板、风格控制、人工审核），避免出现“相似真人”
- 云端 LLM 厂商选型留到实施计划阶段决定，需考虑国内合规和成本
- 实时引导的提示策略需要在真机上做大量调优，避免“话太多”和“反应慢”
- 双机模式的权限模型要谨慎处理：辅助机能看到哪些画面、能否查看拍后照片、是否允许远程切换镜头，都需要单独授权
- V2 Android 接入时机以 HarmonyOS V1 数据为依据
- V2 拍照地图的 POI 数据来源（鸿蒙地图 / 自建）会显著影响成本和体验，需要在 V1 上线后评估
